# 1024上下文连续LRU故障实验

## 结论

即使运行上下文与模型编译的1024 KV buffer lens完全匹配，当前RKNN3 checkpoint路径在连续自动淘汰/恢复时仍可能阻塞整个推理守护进程。因此此前把故障完全归因于4096与1024不匹配并不充分；配置不匹配是风险因素，但自动LRU保存本身也尚不具备生产可靠性。

## 现象

使用约250 Token历史依次创建五个会话。第五个会话触发第一次LRU，成功生成约43 MiB的 `kv4096-1.kv`。随后恢复第一个会话需要再次淘汰第二个驻留会话，生成的 `kv4096-2.kv` 为0字节，守护进程此后不再响应Unix Socket请求。

文件名沿用了实验脚本中的 `kv4096-*` 标识，但本轮进程环境和模型参数均已确认是1024；文件名前缀不代表本轮上下文配置。

## 生产修复

自动LRU checkpoint暂时禁用。当已有4个用户Session时，第5个新会话返回明确错误：

```text
session capacity reached; clear an idle conversation before retrying
```

这样不会调用不稳定的连续checkpoint链路，也不会牺牲已有四个会话。后续只有在厂商SDK升级、显式换出单独压力测试和连续换出恢复测试均通过后，才重新启用LRU。

修复后实机回归确认：第五会话按预期返回容量错误，第一个驻留会话仍能准确召回自己的代号，守护进程保持在线。
