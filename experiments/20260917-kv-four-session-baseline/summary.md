# 四会话 KV Cache 隔离基线

## 目标

验证四个 RKNN3 Session 的历史互不串话、第二轮实际复用 KV Cache，以及完全清理后复用和会话事实归零。

## 方法

四个会话分别写入唯一代号 `JADE-17`、`EMBER-29`、`COBALT-43`、`LOTUS-61`，随后交替询问各自代号。最后完全清理 A 会话，再询问相同问题。直接连接 Daemon Unix Socket，以 RKNN3 `RKLLMRunState` 为指标来源。

## 已验证结果

| 阶段 | 样本 | 平均 TTFT | 平均总耗时 | 平均复用 Token |
|---|---:|---:|---:|---:|
| 首轮写入 | 4 | 189.64 ms | 303.91 ms | 0 |
| 二轮召回 | 4 | 105.19 ms | 173.40 ms | 65.25 |
| 完全清理后 | 1 | 186.48 ms | 198.85 ms | 0 |

四个会话全部准确回答自己的代号，没有出现其他会话代号，准确率 100%、串话数 0。第二轮每个 Session 复用 65–66 Token，平均 TTFT 相比首轮下降 44.53%。A 会话完全清理后回答“不知道”，`reused_tokens=0`。

## 重复实验发现的故障

计划的五轮重复采样在跨轮 Session 周转时长时间阻塞。Daemon 日志明确显示：零 Token Session 被 LRU 选择后，`rknn3_session_save_kvcache` 报 `n_token is invalid`，继而 `SaveKvcacheCheckpointAck` 和内存销毁 ACK 超时。实验被受控停止，临时 KV 文件已清理。

代码侧发现两个问题并已修复：容量判断错误地通过包含 bootstrap 的容器尺寸判断；完全清理只清 KV、没有从 Session 池移除对象。现在容量只统计用户 Session，完全清理后销毁对象，换出保存失败也会显式报错而不是继续破坏状态。

## 当前限制

ACK 超时后，RK1828 重新初始化报告 DDR 地址请求失败，随后新 Daemon 停在权重同步阶段。软件修复已经交叉编译并部署，但五轮 P50/P95 回归必须等 RK1828 冷复位后执行。因此本报告只将首轮四会话结果标为有效结论，不伪造或外推 P95。
