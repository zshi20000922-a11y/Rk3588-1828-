# RK1828 上下文容量扩展实验

## 目的与方法

比较 `max_context_len=1024/2048/4096` 时相同650 Token输入的固定容量开销，并在2048和4096档分别增加1650、3650 Token负载，观察长文本 Prefill 的扩展趋势。每个工作负载运行三次，每次创建新 Session，结束后完全清理 KV；测试期间 `max_new_tokens=16`，减少 Decode 对实验时间的影响。

## 固定650 Token负载

| 最大上下文 | LLM TTFT均值 | Prefill TPS均值 | TPOT均值 |
| ---: | ---: | ---: | ---: |
| 1024 | 594.32 ms | 1093.96 | 13.09 ms |
| 2048 | 590.01 ms | 1101.68 | 12.99 ms |
| 4096 | 594.36 ms | 1093.64 | 13.02 ms |

三档结果接近，说明当前 RKNN3 实现下，仅提高最大上下文配置没有给650 Token请求带来可测的固定性能损失。

## 长输入扩展

| 最大上下文 | 实际输入 Token | LLM TTFT均值 | Prefill TPS均值 | TPOT均值 |
| ---: | ---: | ---: | ---: | ---: |
| 2048 | 1650 | 1443.17 ms | 1143.34 | 13.08 ms |
| 4096 | 3650 | 3191.33 ms | 1143.75 | 13.67 ms |

Prefill TPS在两个长输入档几乎一致，TTFT随实际输入 Token 数近似线性增长。3650 Token仍能成功完成推理和 KV 清理，因此板端默认上下文由1024提升为4096。

## 内存观察

| 最大上下文 | 请求前 RSS | 请求后 RSS | 请求前 VmHWM | 请求后 VmHWM |
| ---: | ---: | ---: | ---: | ---: |
| 1024 | 58,656 kB | 69,524 kB | 113,692 kB | 113,692 kB |
| 2048 | 58,660 kB | 74,928 kB | 113,696 kB | 113,696 kB |
| 4096 | 58,656 kB | 85,672 kB | 113,692 kB | 118,520 kB |

这是 RK3588 宿主进程 RSS，不等同于 RK1828 设备侧 KV 内存。由于厂商当前未提供可信的设备内存细分接口，本实验不能据此推断 RK1828 KV 的绝对大小。

## 限制与下一步

重复的 `item` 文本适合性能测量，但高占用档回答质量没有语义意义。后续需要使用真实多轮对话测试 KV 复用、四会话交替、LRU 换出与恢复，并增加8192档；在没有完成四会话长时间稳定性之前，不将8192设为默认值。
